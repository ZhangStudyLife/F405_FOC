# MT6835 反复故障：寄存器核对与实机结果

2026-10-03；源码基于 `c35fbbd`。本轮没有解决反复欠压告警。已修正初始化等待时间，完成构建、保留参数烧录和回读核对；电机最终停机并保留编码器故障。

## 本轮实际证据

原始数据目录：`build/bench_debug/20261003_145940/`。`fault_sram.bin`、`fault_after_sram.bin` 均在串口确认功率关闭后，以 HOTPLUG 暂停读取，未先复位。原板上程序与归档的 `original_Debug.bin` 完全一致，SHA256 为 `284ef5bf4f67c7914fabd75c22f3963ca289983aa00a2827674ef1ae6e5012fb`。

| 现场 | 角度/状态/CRC 四字节 | 独立重算 CRC | 收到 CRC | STATUS | 累计编码器异常 |
|---|---|---|---|---|---|
| 修改前首异常 | `86 48 8C 28` | `28` | `28` | `4`，欠压 | 680 |
| 延长启动等待后首异常（有效 clear 后） | `89 FB B4 B7` | `B7` | `B7` | `4`，欠压 | 6651 |

两份现场的 ADC、BSP 时序、编码器时序、UART 四项错误计数均为 0。累计编码器异常包括所有拒绝类型，不能根据一个首帧把其余 679/6650 帧全部归类为欠压，也不能直接将累计数换算成一次连续欠压的时长。

这些回包的 CRC 覆盖状态位。当前解码代码与独立逐位 CRC 计算一致，`4` 不是把 CRC 错误误译为欠压。CRC 有效也不保证欠压时的角度准确，更不能仅据数字回包确认芯片 VDD 的真实波形。

## 官方文档与实际寄存器

依据：[MagnTek MT6835 Rev.1.3 官方手册](https://www.magntek.com.cn/upload/pdf/202407/MT6835_Rev.1.3.pdf)，本轮 PDF 和提取文本已归档。

| 项目 | 手册依据 | 当前核对 |
|---|---|---|
| 工作电压 | p.5–6：3.0–5.5 V | 未测芯片 VDD；ST-Link 约 3.11–3.15 V 仅为探针参考读数 |
| 上电时间 | p.6：TPwrUp 典型 64 ms，VDD 上升时间 <100 µs | 原驱动仅等 20 ms，改为 70 ms；手册未给最大值，不能承诺任意慢上电均满足 |
| SPI 模式/频率 | p.20：mode 3，时钟周期至少 60 ns | mode 3，10.5 MHz，标称周期 95.24 ns |
| 片选时序 | p.20：建立时间至少 100 ns，保持时间至少半个 SCK 周期 | 源码/反汇编已检查；无逻辑分析仪，未实测引脚边沿，未宣称已证明建立时间合规 |
| 角度读取 | p.26：`A0 03` 后连续读取 0x003–0x006 | 当前命令、字节排序、21 bit 解码一致 |
| 状态位 | p.25/32：0x005[2:0] 只读；bit0 超速、bit1 弱磁、bit2 欠压 | 两次首帧均为 bit2 |
| CRC | p.25/32：角度21位+状态3位，poly 0x07，MSB first | 与本工程一致 |
| 软件复位/清告警 | p.21、31–37 公开命令及寄存器表 | 没有公布软件复位、欠压阈值设置或写清告警命令；不能向保留寄存器猜写 |

停机读寄存器各重复三次，结果一致：`0x001=00`，`0x007=3F`，`0x008=FC`，`0x009=00`，`0x00A=00`，`0x00B=00`，`0x00C=00`，`0x00D=07`，`0x00E=38`，`0x011=05`，`0x113=00`。原始返回见 `register_readback.json`。

方向为默认 CCW；滞回为 0.011°；带宽档位 5；GPIO 驱动为默认；NLC_EN=0。未发现这些设置相对于已有记录被改坏。未写编码器 EEPROM、零位、NLC 或带宽。状态之后自行恢复为 0，说明本次不需要写清寄存器；手册没有给出完整欠压检测阈值、去抖或恢复特性。

## 开源对照

[SimpleFOC MT6835.cpp，版本 ed05aa1](https://github.com/simplefoc/Arduino-FOC-drivers/blob/ed05aa1644de36cbd19f43e8ea5c3edb643cefa9/src/encoders/mt6835/MT6835.cpp) 的命令、角度拼接、CRC 和状态位定义与本工程一致，也没有软件复位接口。其驱动默认不检查 CRC，并把状态交给调用者读取；这种 API 行为不能作为本机忽略欠压保护的依据。

[SimpleFOC 工程讨论](https://community.simplefoc.com/t/mt6835-angle-sensor-21bit/2910) 讨论了磁场、线性误差及校准，没有提供可核实的欠压软件清除方案。更改滞回、带宽或 NLC 用于改变角度输出，不等于修复欠压。

本仓库 `3f59f51` 与当前版本的 `mt6835_decode()` 完全相同，最近速度控制修改没有新加这项 CRC/状态拒绝条件。这不能证明整个工程不存在其他问题，但排除了“本次才把 bit2 当作错误”的解释。

## 实测与限制

1. 临时 SRAM 程序在功率关闭、ADC 触发关闭、CPU 轮询 SPI 的条件下，按标称 20 kHz 请求读取。10.5 / 5.25 / 1.3125 MHz 各 200000 帧，三组均 CRC 错误 0、状态告警 0、超时 0。结果见 `ram_probe_read.txt`、`ram_probe.c`。这不是运行中的 DMA/PWM 对照，也不能证明降速可修复故障。程序仅驻留 SRAM，之后复位恢复正式固件。
2. 原 Debug 固件的完整 DMA/ADC/UART 停机路径采集 60 秒，日志无故障；随后 SRAM 累计 3882363 次采样、编码器错误 0。见 `dma_idle_before.csv` 与 `dma_idle_before_sram.bin`。
3. 修改启动等待后，Debug/Release 均构建成功。Release 保留参数烧录并校验成功。`postflash.csv` 起始 4 帧已为编码器故障，脚本随后接受了一次 clear。之后 +1 / −1 / 0 rpm 各约 4 秒，功率开启累计 12.024 秒，总 Iq 目标绝对峰值 0.316133 A，短测段无故障。stop 后再次读到故障 1，并取得上述第二个首异常。
4. 这次在欠压原因未明确时进行短测并清错不符合本轮应保持停机的判断，已停止后续运行。短测不能作为故障修复、低速跟随或长期可靠性通过的证据。日志中 +1 rpm 段仅约 17.7° 原始角度行程，不能以目标值代替实测转速。
5. 讨论过把停机告警角度当作有效反馈，复核后撤回；此修改未烧录。最终源码及板上固件仍拒绝 CRC 错误和全部三种状态告警，未放宽保护。也未修改 SPI 时钟或片选时序。

原始 `initial.csv/json` 被后续停机脚本覆盖，不能当作本轮开始记录；它们与 `after_short_test_stop.csv/json` 对应。修改前的证据以独立保存的 `fault_sram.bin` 和 `flash_before.bin` 为准。`postflash_result.json` 在关闭采集线程之前统计，实际 CSV 为 11280 帧，以 CSV 和 `results.json` 为准。
