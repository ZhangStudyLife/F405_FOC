# MT6835 间歇欠压：第二轮停机排查

本轮没有确认间歇欠压的根因，也没有完成修复。没有修改告警判据、控制参数或编码器配置；临时采集代码已经移除，并恢复本轮开始时的正式固件。

实机工作时间：2026-10-03 16:30～16:51，约 21 分钟；电机功率开启时间为 0。随后仅离线分析历史日志。原始数据位于 `../../build/bench_debug/20261003_163000/`。

## 1. 用户所说的“clear 没用”不能只归因于锁存

重新分析 `D:/Downloads/bb14305尝试修复报错.csv`，共发现 9 次从故障状态恢复为无故障：命令计数递增、最近命令结果为成功，随后再次发生故障。恢复后到下一次故障的时间分别为 4.206、225.976、6.798、60.834、3.188、6.158、2.694、20.458、18.866 秒。其中包括一次校准故障的恢复，不能全部当成编码器欠压。

这说明历史记录中确实存在“清除后又报错”，并非全部属于故障没有清除。还有连续 5.084 秒原始角度为 NaN 的区间；该区间内能看到 13 次被拒绝的命令。此时源码的 `clear` 条件要求编码器读数有效，因此不能通过检查。

日志没有命令文本，不能把所有被拒绝命令都认定为 `clear`；500 Hz 快照也不能还原命令执行瞬间的全部 20 kHz 状态。逐项结果见本轮 `clear_log.json`，行号从 CSV 首个数据行的 0 开始。

本轮开始时，同样是“锁存故障码 1，但当前角度有效”：`initial_stop.json` 的 `encoder_valid=1`、`power_on=0`。这只描述当时状态，不否定用户遇到的持续无效情况。

## 2. 先保存当前现场，再做对照

在发送并确认 stop 后，使用无复位连接暂停 MCU，保存完整 SRAM 和 Flash。正式程序与本地 Release 完全一致。

- 首异常仍为 `89 FB B4 B7`，独立计算 CRC 为 `B7`，低三位状态为 `4`。
- 编码器累计异常为 16949；这个计数包含所有拒绝类型，不能把全部异常都归为欠压，也不能换算为一段连续欠压时间。
- ADC、BSP 时序、编码器时序及 UART 未见错误，功率关闭。

`fault_sram.bin` 保留了原始故障，后续 MCU 复位不会改动这个文件。

## 3. 绕过原 DMA 驱动的独立读取

临时程序仅放入 SRAM，停止控制采样与中断、保持功率关闭，以 CPU 轮询 SPI。没有发送编码器寄存器写入、EEPROM、零位或复位指令。

以下三组按相同顺序重复两轮，每组每轮 20 秒：

| 读取方式 | SPI 频率 | 完整角度组率 | 两轮完整组数 | CRC 错误 / 状态告警 / 超时 |
|---|---:|---:|---:|---:|
| A0 03 连续读取 | 10.5 MHz | 20 kHz | 800000 | 0 / 0 / 0 |
| A0 03 连续读取 | 1.3125 MHz | 20 kHz | 800000 | 0 / 0 / 0 |
| 依次读取 003、004、005、006 | 1.3125 MHz | 1 kHz | 40000 | 0 / 0 / 0 |

合计 164 万组。逐寄存器方式每组有四笔 SPI 事务；不能把组数与事务数混为一谈。片选建立等待至少 40 个 CPU 周期，保持等待至少 80 周期。

同时用 ADC1 的 VREFINT 和芯片出厂校准值估算 **MCU VDDA/VREF+**：校准原码 1505，采样原码总范围 1501～1508，换算约 3.293～3.309 V，各组均值换算约 3.300～3.301 V。ADC 时钟 21 MHz，采样时间 480 周期，约 22.9 μs。

这是 MCU 模拟电源的间接估计，包含参考电压、ADC 和温度误差；不是编码器 9 脚相对 12 脚的测量，也不能发现所有短脉冲。ST-Link 同时报出的约 3.11～3.15 V 不是这个 ADC 结果，不能用探针读数直接认定编码器欠压。

本对照没有复现问题，不能据此认定降 SPI 频率能修复。低频测试只用于隔离读取，未应用到正式 20 kHz 控制路径。

## 4. 原有 ADC → SPI DMA → 控制 → UART 路径

临时诊断固件保留原有运行逻辑和保护，只增加原始报文环形记录、独立 CRC 计数与状态变化记录。目的是抓住新异常前后的报文，不允许异常角度进入控制，也不启动电机。

在暂停读取前累计处理 **9323529 帧**，按 20 kHz 对应约 466.176 秒：

| 项目 | 实测 |
|---|---:|
| CRC 错误 | 0 |
| STATUS=0 | 9323529 |
| STATUS=1～7 | 全部为 0 |
| 编码器异常计数 | 0 |
| ADC / BSP 时序 / 编码器时序 | 全部为 0 |
| UART 四项计数 | 全部为 0 |
| 最大采样处理时间 | 3766 CPU 周期，约 22.42 μs |

其中 UART 连续记录 150027 帧，约 300 秒，全部功率关闭、故障码 0、丢帧计数 0。UART 记录从固件启动后才开始，时长短于 MCU 计数覆盖范围。始终没有异常触发，环形缓冲保存的是末尾正常数据，不是故障波形。

实读公开配置仍为 `001=00, 007=3F, 008=FC, 009=00, 00A=00, 00B=00, 00C=00, 00D=07, 00E=38, 011=05, 113=00`，各重复三次一致。另只读归档了 `00F=00, 010=00, 012=A0`；它们属于厂商保留区，没有赋予未经公开的含义，也没有写入。全部见 `register_readback.json`。

## 5. 仍缺少什么证据

当前公开手册将 STATUS[2] 定义为供电欠压告警，状态位只读；没有公开欠压比较器的阈值、迟滞、去抖、锁存/恢复细节，也没有可核实的软件复位命令。CRC 正确证明收到的状态与校验一致，不等于已测到真实 VDD 波形，也不证明欠压状态下角度仍然可靠。

本轮无法区分的仍是：告警发生时的芯片端供电/地、电气通信问题，或芯片内部告警行为。不能仅靠正常时的数百万帧和稳定均值作出取舍。

下一次有效诊断需要在故障仍存在时，先记录 `clear` 的命令计数和结果、实时原始角度是否持续 NaN，以及原始 SPI 报文；在清错、复位或插拔之前保存。若有示波器，同步观察芯片 **9 脚 VDD 对 12 脚 VSS** 和芯片端 CSN/SCK，才能把告警时刻与电气现象关联。若故障当刻这两项均符合规格，需要原厂说明 STATUS[2] 的具体触发与恢复条件，并用替换芯片作对照；当前材料不足以选择所谓 reset 寄存器。

用户已确认发过 clear 但无效；尚未获得对应本轮故障的命令结果，或芯片引脚处的具体电压读数/波形。本轮没有要求靠反复 clear 继续带电运行。
